# Офлайн-калибровка: что, чем и как измерено

Все калибровочные данные получены **только** из разрешённого датасета кейса
(`~/Downloads/dataset/data`, 122 прогона, 36.7 часа, 8.8 млн сообщений) и
используются исключительно офлайн: в online-контуре GNSS не участвует.

Скрипты лежат в `~/tram_ws/tools` (вне поставки), результат — в `config/`.

---

## 1. Шаг 1. Разведка данных (`tools/survey.py`, `tools/dive.py`)

Для каждого прогона: частоты, диапазоны, расхождение тележек, связь скорости
колёс со скоростью GNSS.

Результаты, приведшие к ключевым решениям:

| наблюдение | значение | вывод |
|---|---|---|
| `v_колёс / v_GNSS` (МНК) | **1.000207** | канал в км/с → коэффициент 1/3.6 |
| RMSE `v/3.6 − v_GNSS` | 0.072 м/с | перевод подтверждён |
| максимум колёс / GNSS | 53.33 / 14.82 | 53.33/3.6 = 14.81 м/с |
| расхождение тележек σ | 0.127 м/с, p99.9 = 2.1 | есть участки с расхождением (скольжение) |
| GNSS-позиции, 2-я разность | 0.005 м | GNSS уровня RTK (шум мм) у большинства прогонов |
| GNSS-скорость, 4-я частота | до 20 Гц (две антенны) | master и rover — разные приёмники, смещение ~12 м |
| `dt` в записях | 0.8 мс … 0.9 с | сообщения приходят пачками, интегрирование по меткам |
| одиночные сбои ручки | 0.118 % отсчётов | нужен медианный фильтр |
| число GNSS-топиков | 86 прогонов master+rover, 1 только rover, 35 без GNSS | GNSS только для начальной привязки |

## 2. Шаг 2. Геометрия трассы (`tools/route.py`, `tools/build_map.py`)

Все прогоны проходят по одному пути депо в двух противоположных направлениях
(траектории совпадают после поворота на 180°).  Кривизна достигает
**1/14 км** (радиус 14 м) — это депо со стрелками, часть прогонов идёт по другой
ветке.  Отсюда вывод: направление движения из разрешённых сигналов
**не выводится** в принципе, и позиционирование возможно только привязкой к
карте пути (что кейс и предусматривает).

Проверка воспроизводимости траекторий: жёсткое (с подгонкой масштаба и
поворота) совмещение прогонов с картой даёт остаток 2–10 м при масштабе
0.995–1.002, т.е. трасса повторяется от прогона к прогону.

## 3. Шаг 3. Характеристика тягового привода (`tools/calibrate.py`)

Порядок действий:

1. сигналы приводятся к сетке 20 Гц, скорость сглаживается скользящим
   средним 0.55 с, ручка проходит медианный фильтр 5 (устранение сбоев);
2. для каждой ячейки (ручка × скорость) считается среднее взвешенное
   ускорение (2.6 млн отсчётов, 31 × 16 ячеек);
3. пустые ячейки заполняются ближайшей валидной (2-D nearest neighbour) и
   слегка сглаживаются; верхняя ячейка по скорости достраивается по закону
   постоянной мощности;
4. из строки `u = 0` МНК-оцениваются коэффициенты сопротивления.

Полученная характеристика `a_nom(u, v)` (м/с²) — ось `u` = −15…+15, строки

| 4 | −0.47 | −0.71 | −0.78 | −0.67 | −0.58 | −0.13 | −0.01 | 0.08 | 0.38 | 0.45 | 0.85 | 0.91 | 0.94 | 0.93 | 0.90 |

Ключевые особенности, ради которых модель нелинейная и табличная:

* максимум тяги при `u = +9…+10`, плато и спад к `u = +15`;
* **ступень при `u = −8`**: −0.28 м/с² при −0.79 (−7) и −0.93 (−9);
* монотонный спад тяги по скорости (режим постоянной мощности);
* при нейтрали `|a| < 0.03 м/с²` — средний уклон пути близок к нулю.

Попытка описать ту же характеристику параметрической формой
`T(u)/(1+(v/v_k)^p)` (МНК, 37 параметров) даёт остаток 0.17 м/с², но
параметры `T(u)` неинтерпретируемы (не монотонны) — вырожденность задачи
«сила × скоростная характеристика».  Поэтому в решении используется
таблично-аппроксимирующая (гибридная) форма: таблица даёт номинальное
ускорение, аналитический вид используется для экстраполяции за пределы
калибровки (закон постоянной мощности) и для ограничения по сцеплению.

Оценка неопределённости модели: поузловой стандартный разброс ускорения внутри
ячейки (между прогонами) — 0.10–0.20 м/с² в движущихся ячейках и 0.03–0.05
м/с² на нейтрали.  Это и есть шум модели, задающий `ekf.q_model_sigma`.

## 4. Шаг 4. Сопротивление и сцепление

Из строки `u = 0` (v ≥ 3 м/с) МНК с мягкой регуляризацией:

```
F_res(v)/m = 0.0399 − 2.91e−4·v − 1.385e−4·v²      →  C_rr ≈ 0.0041
```

Предел сцепления `μ = 0.25` (F = μ·m·g = 98 кН при m = 40 т) задан
конфигурацией и в калибровке не участвует: в датасете нет участков
с реализованным пробуксовыванием сцепления, но есть скольжение, поэтому
фактический `μ` оценивается online и публикуется в диагностике.

## 5. Шаг 5. Карта трассы (`tools/make_map.py`)

Для каждого направления движения:

1. отбрасываются прогоны без GNSS и прогоны, у которых длина GNSS-полилины
   расходится с интегралом скорости колёс более чем на 2.5 % (признак
   «глитча» в GNSS);
2. самый длинный прогон служит seed, остальные (длина ≥ 90 % seed)
   подмешиваются по узлам, берётся **медиана** (подавляет выбросы GNSS);
3. лёгкое сглаживание геометрии (±1 узел, 2 прохода) и пересчёт
   равномерной дуги 1 м;
4. профиль высоты — два прохода медианного фильтра (31 м) и скользящее
   среднее 101 м (канал alt GNSS содержит скачки до 60 м и дрейф).

Итог: две ветви (оба направления), по ~5.5 км, 5580 и 5513 узлов.
Повторяемость профиля высоты между прогонами: 0.7–1.0 м RMS, что много лучше
собственного шума канала (±10 м) и означает, что профиль высоты карты
пригоден для публикации `z`.

## 6. Шаг 6. Калибровка масштаба одометрии

Масштаб `wheel_unit_scale` = 1.000207 определён по скорости (МНК, все
прогоны).  Дополнительно в online-контуре выполняется одноразовая
калибровка масштаба **пути** по окну GNSS: `ratio = ∫v_GNSS dt / s_одометрии`.
Используется именно интеграл скорости, а не длина GNSS-полилинии: в части
прогонов координаты шумят на 2–4 м, из-за чего длина пути завышается в 2 раза
(измерено: 285 м полилинии против 143 м одометрии на одном и том же участке).

На 87 прогонах с эталоном полученные значения `ratio`: 0.987…1.015, медиана
≈ 1.006, что соответствует дрейфу пути 0.1–1.5 % на 5.5 км.

## 7. Воспроизведение калибровки

```bash
cd ~/tram_ws
source /opt/ros/humble/setup.bash && source install/setup.bash
python3 tools/extract.py        # 122 прогона -> calib/runs.pkl   (~12 мин)
python3 tools/calibrate.py      # -> src/tram_backup_odometry/config/model.json
python3 tools/make_map.py       # -> src/tram_backup_odometry/config/route_map.json
python3 tools/survey.py         # сводка по данным
python3 tools/quality.py        # статистика сбоев входных сигналов
```

Артефакты `model.json` и `route_map.json` входят в поставку пакета, поэтому
сборка и проверка решения **не требуют** запуска калибровки.
