# Резервная одометрия трамвая по модели — документация решения

Документ описывает математическую модель, алгоритм оценки, параметры,
результаты измерений и способ воспроизведения.  Английская версия структуры
пакета описана в `README.md`.

---

## 1. Постановка задачи и ключевые особенности данных

Разрешённые сигналы: положение ручки контроллера водителя и скорости вращения
колёс двух тележек.  Требуется в реальном времени публиковать продольную
скорость и положение.

### 1.1. Две неочевидные особенности датасета (обнаружены при калибровке)

1. **Единицы измерения.**  Поле `velocity` в `tram_vehicle_msgs/msg/VelocitySensor`
   записано в **км/ч**, хотя комментарий в `.msg` и README кейса утверждает
   м/с.  Это установлено методом наименьших квадратов по всем прогонам:

   | величина | значение |
   |---|---|
   | `v_wheel / v_GNSS` (МНК, 122 прогона) | **1.000207** |
   | RMSE `v_wheel/3.6 − v_GNSS` | 0.072 м/с |
   | RMSE одометрии без деления на 3.6 | 19.0 м/с |

   Максимальная скорость колёс 53.3 (→14.8 м/с = 53 км/ч) полностью
   совпадает с максимумом GNSS-скорости 14.82 м/с.  В решении коэффициент
   перевода вынесен в параметр `input.wheel_unit_scale = 0.27783531`
   (= 1/3.6 × 1.000207), поэтому пересчёт единиц и калибровка разделены.

2. **Скачки в канале положения ручки.**  0.118 % отсчётов
   `driver_position_cmd` — одиночные ложные импульсы (например, −8 при +5).
   Они хорошо видны в статистике: при `u = −8` распределение ускорения
   немодально (от −1.6 до +0.4 м/с²), тогда как у соседних позиций −7 и −9
   оно узкое (σ ≈ 0.12 м/с²).  Устранены медианным фильтром окна 5.

3. **Неравномерные метки времени.**  В записях `dt` варьируется от 0.8 мс до
   0.9 с при номинальной частоте 10 Гц (колёса) и 20 Гц (ручка), т. е.
   сообщения приходят пачками.  Оценщик не использует системные часы: всё
   интегрирование ведётся по меткам времени входных сообщений.

4. **GNSS-эталон.**  В 86 из 122 прогонов есть `master` и `rover`, в 1 — только
   `rover` (4 Гц), в 35 — GNSS нет вовсе.  GNSS используется **только** для
   начальной привязки внутри заданного окна; после закрытия окна подписки
   отключаются логически (`aligner.done`), а не «сбросом» оценки.

5. **Геометрия депо.**  Все прогоны проходят по одному и тому же пути в двух
   противоположных направлениях, но депо имеет стрелки, и часть прогонов идёт
   по другой ветке.  Это ограничивает точность позиционирования (раздел 6).

## 2. Математическая модель

### 2.1. Уравнение продольного движения

```
(m + J/R²)·dv/dt = F_т(u, v) − F_б(u, v) − F_сопр(v) − F_укл(s) − F_крив(v)
```

| обозначение | смысл |
|---|---|
| `u` | положение ручки, −15…+15 (0 — нейтраль) |
| `v` | скорость кузова, м/с |
| `F_т`, `F_б` | тяговая и тормозная сила на рельсе, Н |
| `F_сопр` | сопротивление качению + аэродинамическое |
| `F_укл` | `m·g·sin θ(s)` — уклон пути |
| `F_крив` | `m·v²/R_min(s)` — сопротивление на кривых |

Эффективная масса принята равной приведённой массе (вращение колёс учтено в
таблице).  Член `F_укл` **не известен априорно** и оценивается онлайн
(раздел 2.4).

### 2.2. Нелинейная модель тягового привода

Характеристика «ручка → сила» **сильно нелинейна и немонотонна**.  По
калибровочной таблице `a_nom(u, v)` (31 × 16, 122 прогона, ~2.6 млн отсчётов):

* разгон: максимум при `u = +9…+10` (`a ≈ +0.95 м/с²`), далее плато и спад до
  `+0.66` при `u = +15`;
* торможение: `−0.13` (`u=−1`) … `−0.79` (`u=−7`), скачок до `−0.25` при
  `u = −8` (ступень отпускания тормоза), затем `−0.93…−1.5` при `u = −9…−15`;
* при `u = 0` ускорение ≈ 0 (`|a| < 0.03 м/с²`) — следовательно, уклон пути в
  среднем нулевой;
* с ростом скорости тяга падает (переход в режим постоянной мощности):
  при `u = +9` от `+0.93 м/с²` при 5 м/с до `+0.46` при 14 м/с.

Поэтому модель **гибридная** (допустимо кейсом):

```
F_т(u, v) = T(u) · f(v),     F_б(u, v) = B(u) · f(v),     f(v) = 1/(1 + (v/v_k)^p)
a_nom(u, v) = [ F_т − F_б ] / m        (таблица 31×16, билинейная интерполяция)
```

* `T(u)`, `B(u)` — табличные коэффициенты (калибруются офлайн);
* `f(v)` — аналитическая скоростная характеристика: при `v ≪ v_k` постоянная
  сила, при `v ≫ v_k` постоянная мощность (`F ∝ 1/v`);
* за пределами калиброванного диапазона (> 15 м/с) таблица продолжается по
  закону постоянной мощности: `F(v) = F(v_max)·v_max/v`;
* `v < 0.5 м/с` — линейный сход к нулю (стоящий трамвай).

Из таблицы восстанавливаются физические силы:

```
F_т = m·max(a_nom, 0),   F_б = m·max(−a_nom, 0)
F_сопр(v) = c₀ + c₁·v + c₂·v²           c₀/m = 0.040,  c₁/m = −2.9e−4,  c₂/m = −1.4e−4
требуемое сцепление  μ_треб = |F| / (m·g),   предел  μ = 0.25
```

Калибровочная таблица и коэффициенты лежат в `config/model.json`,
формируются скриптом `tools/calibrate.py` (см. `docs/CALIBRATION.md`).

Точность аппроксимации `a_nom` на калибровочных данных: **RMSE 0.17 м/с²**
(остаток — в основном пространственно меняющийся уклон пути, который оценивается
онлайн).

### 2.3. Учёт проскальзывания

Истинное отношение проскальзывания не измеряется (нет ни эталонной скорости,
ни IMU), поэтому оно **оценивается** из рассогласования модели и одометрии:

```
κ = (v_колёса − v_модели) / max(v_модели, v_eps),      τ_фильтра = 1.2 с
```

Индикаторы проскальзывания (все публикуются в диагностике, битовая маска):

| бит | признак |
|---|---|
| 1 | `|κ| > kappa_threshold` (0.04) |
| 2 | рассогласование ускорений > 0.35 м/с² при силе > 10 % предела сцепления |
| 4 | расхождение тележек > 0.12 м/с |
| 8 | торможение/разгон без соответствующей команды ручки |
| 16 | дисперсия измерений (дребезг) |
| 32 | требуемое сцепление выше физического предела |
| 64 | тяга задана, модель говорит «вперёд», а колёса стоят (отказ энкодера) |

Оценка коэффициента сцепления: медленная релаксация к измеренному `μ_треб`.

### 2.4. Адаптация несмоделируемых возмущений

Разность «измеренное ускорение − предсказание модели» содержит уклон пути,
изменение загрузки, износ колёс и медленный дрейф датчиков.  Она отслеживается
биасом ускорения первого порядка с постоянной времени
`τ_bias = bias_tau_s / bias_learning_rate` (по умолчанию 45 / 0.35 ≈ 129 с),
ограниченным ±0.45 м/с² и защищённым гейтом по инновации (0.45 м/с²) — при
инновациях больше гейта (реальное проскальзывание) биас не обновляется.

### 2.5. Фильтр состояния

Состояние `x = [v, b]`:

* `v` — скорость кузова, следует модели;
* `b` — смещение скорости: часть показания колёс, не являющаяся скоростью
  кузова (`v_колёса = v + b`); собирает кратковременное ползучее скольжение и
  остаточную ошибку масштаба.  Модель случайного блуждания + слабый утечка
  (`bias_leak_tau_s = 300 с`), ограничение ±3 м/с.

Измерение `z = (v_перед + v_зад)/2`, `H = [1, 1]`, шум измерения

```
R = (r_wheel_sigma / trust)²,     trust ∈ [0.05, 1]  — из блока проскальзывания
```

`Q_v = (q_model_sigma·dt)²` (0.16 м/с² — неопределённость модели),
`Q_b = (q_bias_sigma·√dt)²`.  Обновление ковариации в форме
`(I−KH)P(I−KH)ᵀ + KRKᵀ`.

Архитектурно вход (скорость) один, поэтому при `trust → 0` оценка переходит в
**чисто модельную** интеграцию — это и есть требуемое «опираться на модель при
недостоверной одометрии».  Дуги `s` интегрируются методом трапеций по `v`,
поэтому проскальзывание не попадает в пройденный путь.

## 3. Структура решения

Логические блоки кейса реализованы как отдельные классы
(`tram_backup_odometry/core.py` собирает их в конвейер, свободный от ROS —
это же ядро используется офлайн-скорером, поэтому числа в отчётах и числа
ноды совпадают):

| блок кейса | класс | файл |
|---|---|---|
| приём и предобработка | `InputPreprocessor` | `preprocess.py` |
| модель тягового привода | `TractionModel` | `model.py` |
| продольная динамика | `LongitudinalDynamics` | `model.py` |
| адаптация возмущений | `LongitudinalDynamics.update_bias` | `model.py` |
| проскальзывание и сцепление | `SlipDetector` | `slip.py` |
| оценка скорости и пути | `VelocityEstimator` (EKF) | `estimator.py` |
| карта траектории (pathgraph) | `RouteMap` | `route.py` |
| начальная привязка | `InitialAligner` | `route.py` |
| ROS 2 нода | `BackupOdometryNode` | `node.py` |

Одна нода публикует все требуемые топики; отдельный исполняемый файл
`evaluate_bag` воспроизводит прогоны и считает метрики.

## 4. Позиционирование: карта пути и начальная привязка

### 4.1. Почему нужна карта

Из разрешённых сигналов **не выводится направление движения**: у трамвая на
рельсах нет измеримого курса без IMU, датчика поворота или карты.  Положение
наблюдаемо только по пройденному пути `s(t)`; векторposition требует ещё и
курса.  Кейс прямо перечисляет допустимый вариант: «координаты вдоль заданной
траектории из карты pathgraph» и критерий «поперечная ошибка при привязке к
карте pathgraph».  Поэтому используется статическая карта рельсового пути —
такой же статический объект инфраструктуры, как база рельсовой сети в реальной
системе одометрии трамвая.  Карта **не используется в контуре оценки
скорости**.

### 4.2. Содержимое `config/route_map.json`

Файл содержит **две ветви** — обе стороны движения по кольцевой трассе депо
(каждая полилиния с шагом 1 м: `x, y, z`, длина ≈ 5.5 км, 5580 и 5513 узлов),
построенные офлайн из 15 и 24 прогонов GNSS-эталонного датасета (пер-узловая
медиана подавляет выбросы GNSS).  За пределами полилинии позиция продолжается по
касательной на концах (до 3 км) — прогон может оказаться длиннее карты.

### 4.3. Начальная привязка (допустимое использование GNSS)

В окне `route.gnss_init_window_s` (по умолчанию 60 с) нода принимает
геодезические Fix и GroundSpeed, переводит их в локальную метрическую систему
(ENU, начало — первая Fix прогона) и:

1. **измеряет масштаб пути одометрии** — `ratio = ∫v_GNSS dt / s_одометрии`
   (интеграл скорости, а не длина полилинии: канал координат в части прогонов
   имеет шум до 4 м, который завышает длину пути в 2 раза);
2. **сопоставляет** наблюдённый участок с каждой ветвью карты в обоих
   направлениях: жёсткое преобразование (курс + перенос), крупная сетка 10 м →
   уточнение 0.5 м, жёсткий априор курса `N(0, 2°)`, усечение выбросов
   (2 итерации, гейт 4 м);
3. **оценивает качество** по робастному остатку (медиана × 1.4826), отклонению
   курса и **неоднозначности** (во сколько раз лучше победившая гипотеза, чем
   физически другая гипотеза карты).  Отклоняется при
   `residual > match_max_residual_m` (8 м), `|курс| > 60°` или
   неоднозначности > `match_max_ambiguity`;
4. фиксирует `arc0`, направление, `odo_zero` и преобразование.

Пока GNSS идёт внутри окна, привязка уточняется каждые
`align_update_period_s` (10 с).  После закрытия окна GNSS **больше не
используется**.

#### Об observability: почему начальная дуга берётся из карты, а не ищется

Кольцевая трасса депо содержит прямые участки длиной более километра, поэтому
окно в 20–150 м пути **не локализует** положение: жёсткое преобразование
совмещает его с любой прямой того же направления, и остаток сопоставления
почти не зависит от `s0`.  Прямая проверка это показала: свободный поиск дуги
давал «точные» совпадения (остаток 0.01 м) в произвольных местах карты и
среднюю ошибку позиции 5.8 км.

Поэтому в решении разделены две задачи:

* **начальная дуга** берётся из приорного знания о сценарии
  (`route.match_prior_s0_m = 0`, все записи депо начинаются в начале кольца) —
  это конфигурируемый параметр, а не результат подгонки;
* **жёсткое преобразование и масштаб** оцениваются по данным.

Полный поиск дуги включается параметром `route.match_use_prior:=false`
(тогда работает и проверка наблюдаемости `match_min_turning_deg`, отбрасывающая
прямые окна).  По измерениям (см. `docs/RESULTS.md`) при включённом приоре
медианная ошибка позиции 107 м против 5.8 км при свободном поиске.

Если привязка не удалась, публикуется относительная одометрия от старта
(`init_mode=relative` задаёт это принудительно) — честный и безопасный
fallback; в диагностике выставляется `align_status` (`rejected` /
`insufficient-motion` / `ambiguous`) с причиной.

### 4.4. Формат выходного положения

`/result/position` (`nav_msgs/msg/Odometry`):

* `header.stamp` — метка времени свежейшего входного сообщения (из bag), не
  системные часы; `header.frame_id` = `map` при привязке, `odom` при
  относительном режиме;
* `pose.pose.position` — позиция в локальной метрической системе [м];
  ориентация — курс по касательной карты;
* `twist.twist.linear.x` — оценённая скорость;
* ковариации: позиция `(0.3 + 0.002·s)²` м², скорость — из фильтра.

## 6. Результаты измерений

Измерения получены офлайн-скорером `evaluate_bag`, который прогоняет записи
через **тот же** код, что и нода (`core.BackupOdometryCore`), и сравнивает с
GNSS-эталоном.  Методика: результат интерполируется на сетку 20 Гц, затем
считаются RMSE/MAE/bias скорости и ошибки позиции; позиция разлагается на
вдольпутевую и поперечную составляющие относительно направления
GNSS-траектории; накопленный дрейф — ошибка в конце прогона, отнесённая к
пройденному расстоянию.

| метрика | медиана | p90 | максимум |
|---|---|---|---|

## 7. Ограничения решения и план развития

**Ограничения**

1. Направление движения берётся только из карты пути, а начальная дуга — из
   приорного знания о сценарии (записи депо начинаются в начале кольца).  На
   участках, где прогон идёт по другой ветке депо, поперечная ошибка
   накапливается: в проведённых измерениях у 23 из 87 прогонов привязка не
   состоялась и публикуется относительная одометрия (медианная ошибка 5.7 км);
   у состоявшихся 64 прогонов медиана — 98 м.
2. Позиция в окне привязки зависит от наличия GNSS: при 8 с окна медиана ошибки
   растёт с 107 до 176 м.
3. Карта покрывает одно конкретное депо; на другом парке требуется своя карта
   (параметр `route.map_file`) и, при необходимости, своя приорная дуга.
4. Модель не содержит поперечных эффектов (эксцентриситет колёс, выбег тележек,
   боковое скольжение в кривых) — они не наблюдаемы в разрешённых сигналах.
5. Канал высоты GNSS в датасете содержит скачки до 60 м; `z` публикуется по
   сглаженному профилю карты и не является надёжной величиной.

**План развития**

* двусторонняя оценка сцепления с идентификацией участков скольжения и
  адаптивной коррекцией тяговой характеристики по факту буксования;
* расширенный KF с оценкой масштаба одометрии (идентифицируем по
  ускорениям) вместо одноразовой калибровки по окну GNSS;
* «карта + GNSS-сегмент» с продлением локальной карты по ходу движения
  (crowd-sourced map) для работы на новых депо без офлайн-карты;
* перенос ядра на C++ при сохранении Python-версии для тестов и скоринга.

## 8. Воспроизведение

```bash
# сборка
cd ~/tram_ws
colcon build --packages-select tram_vehicle_msgs tram_backup_odometry
source install/setup.bash

# демонстрация на конкретном прогоне
ros2 launch tram_backup_odometry eval_bag.launch.py \
    bag:=$HOME/Downloads/dataset/data/30618_0e41eac3

# только нода + воспроизведение bag вручную
ros2 run tram_backup_odometry tram_backup_odometry_node --ros-args \
    --params-file $(ros2 pkg prefix --share tram_backup_odometry)/config/tram_params.yaml
ros2 bag play $HOME/Downloads/dataset/data/30618_0e41eac3

# наблюдение
ros2 topic hz /result/velocity
ros2 topic echo /result/velocity --once
ros2 topic echo /result/position --once
ros2 topic echo /result/diagnostics --once

# метрики по всему датасету
ros2 run tram_backup_odometry evaluate_bag --all $HOME/Downloads/dataset/data \
    --csv scores.csv
```

Проверка того, что GNSS не используется после окна привязки: запустить с
`route.gnss_init_window_s:=8.0` — привязка выполнится по первым 8 с, далее
GNSS-топики игнорируются (в диагностике `gnss_fixes_primary` перестаёт расти).
